# ТЗ: Несколько фотографий у сервиса (1–5)
## Для Claude Code · дополнение к TZ_Outside_v5_6 · положить в /docs проекта

## 1. Продуктовые правила
- У сервиса от 1 до 5 фотографий. Минимум 1 — как и раньше, обязательна
- Первая фотография = обложка: показывается в плитке раздела, в избранном и в админ-списке
- Порядок фотографий задаёт автор при создании; на любой миниатюре доступно
  действие «Сделать обложкой» (фото становится первым)
- Редактирование набора фото после отправки — только админ (как и все правки карточек)

## 2. База данных (новая миграция, НЕ править 001)
```sql
-- migrations/00X_service_photos.sql
CREATE TABLE service_photos (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  service_id UUID NOT NULL REFERENCES services(id) ON DELETE CASCADE,
  url        VARCHAR(500) NOT NULL,
  sort       INT NOT NULL DEFAULT 0,          -- 0 = обложка
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_service_photos ON service_photos(service_id, sort);

-- перенос существующих одиночных фото
INSERT INTO service_photos (service_id, url, sort)
SELECT id, photo_url, 0 FROM services WHERE photo_url IS NOT NULL;
```
Колонку `services.photo_url` НЕ удаляем — она становится денормализованной
обложкой (всегда = url фото с sort=0). Обновляется триггерно в коде при любом
изменении набора/порядка. Так плитка и старые запросы продолжают работать без JOIN.

## 3. API
### Создание (POST /services) — меняем
- multipart/form-data: поле `photos` — от 1 до 5 файлов (jpeg/png, каждый ≤ 5 МБ)
- Порядок файлов в запросе = порядок фото (первый = обложка)
- Ошибки: PHOTOS_REQUIRED (0 файлов), TOO_MANY_PHOTOS (>5),
  PHOTO_TOO_LARGE, PHOTO_BAD_FORMAT — в формате { errors: {...} }
- Сохранение: uploads/services/<serviceId>/<uuid>.jpg; после записи строк
  в service_photos выставить services.photo_url = обложка

### Чтение
- GET /services (список): без изменений — photo_url (обложка), + поле photos_count
- GET /services/:id (деталка): + массив
  `photos: [{ id, url, sort }]` отсортированный по sort

### Админ-редактирование (расширить PATCH-раздел)
- POST   /admin/services/:id/photos            multipart 1 файл → добавляет в конец (макс 5)
- DELETE /admin/services/:id/photos/:photoId   (нельзя удалить последнее фото — LAST_PHOTO)
- PATCH  /admin/services/:id/photos/order      { photo_ids: [id,id,...] } → пересортировка;
  первый id в массиве становится обложкой; после любой операции пересчитать photo_url

## 4. Мобильное приложение (когда дойдём до Flutter)
- Форма «Новая рекомендация»: вместо одной зоны фото — горизонтальный ряд миниатюр
  80×80 + плитка «+» (исчезает при 5 фото); на первой миниатюре бейдж «Обложка»;
  долгое нажатие на миниатюру → «Сделать обложкой» / «Удалить»
- Сжатие на клиенте до 1280px по длинной стороне, JPEG ~80%
- Детальный экран сервиса: фото-галерея со свайпом + точки-индикатор (1 из N);
  сердечко-избранное остаётся поверх справа сверху
- Плитка раздела: без изменений (обложка), в углу бейдж «5 📷» если фото больше одной
- Админ-редактирование: тот же ряд миниатюр с «+», удалением и сменой обложки

## 5. Критерии приёмки (чек-лист для Claude Code)
- [ ] Миграция накатывается на базу с существующими сервисами без потери фото
- [ ] POST /services c 3 файлами создаёт 3 записи, photo_url = первый файл
- [ ] POST c 6 файлами → 400 TOO_MANY_PHOTOS; с 0 → PHOTOS_REQUIRED
- [ ] GET /services/:id возвращает photos по порядку
- [ ] Смена порядка админом меняет photo_url на новую обложку
- [ ] Удаление последнего фото запрещено (LAST_PHOTO)
- [ ] Старые сервисы (созданные до фичи) отдают 1 фото и в списке, и в деталке
